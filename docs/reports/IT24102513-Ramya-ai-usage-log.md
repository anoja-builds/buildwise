## 3. Reflection

### 3.1 What AI did well

GitHub Copilot was genuinely useful for generating repetitive but necessary code: entity property lists, navigation-property declarations, LINQ expressions for status resolution, and FastAPI Pydantic models. The boilerplate saved time that was better spent on domain logic and cross-component integration. Claude was strong at producing `vi.mock` patterns and `userEvent` interaction sequences for the React test suite — patterns that would have taken longer to look up from scratch. For the Python microservices, Claude's first-pass FastAPI route structures (`DiscrepancyInput`, `RequestAnalysisInput`, health endpoints, uvicorn startup blocks) were accurate and consistent across both `delivery_agent.py` and `request_agent.py`.

### 3.2 Where AI failed or needed correction

Three classes of failure appeared consistently.

**Cross-component awareness was zero.** The FK ordering bug in the `DeliverySchedule` migration (Session 1) and the port-8001 mistake in `DeliveryAgentService` (Session 3) both happened because the AI had no knowledge of the broader team's architecture. Copilot defaulted to whatever port or table name it had seen most recently in context, which happened to be wrong in both cases. These are the kind of mistakes that slip through if the developer does not actively review generated code against the integration spec.

**DTO shape assumptions were wrong.** The `deliverySupplier()` helper (Session 5) and the initial Python response schema (Session 3) both assumed a more deeply nested data model than the actual API produced. AI generated code that was internally consistent but did not match the real wire format. The supplier name bug was particularly harmful because all existing tests passed — they were also using the wrong fixture shape. The lesson is that AI-generated test fixtures must be validated against real API responses, not just against the component under test.

**Async correctness was missed.** The missing `await` in `DeliveriesController.cs` (Session 7) compiled cleanly and would have silently returned a task object wrapped in HTTP 200. This is a category of error where the AI produces syntactically valid but semantically broken code, and only careful human review catches it.

### 3.3 Lessons learned

1. Always cross-reference AI-generated port numbers, table names, and endpoint paths against the integration specification before running tests. The AI only knows what is in its context window.
2. Write at least one test that uses real API fixture shapes — copied from a real response or from a shared DTO — before accepting AI-generated component code. Fixing the `deliverySupplier()` bug required fixing both the component *and* the test fixtures simultaneously.
3. Async C# code generated by AI should be reviewed line-by-line for missing `await` keywords, especially in controller actions where the return type already wraps `Task<IActionResult>` and the compiler has no way to warn.
4. AI will not volunteer a CSS file. If the visual output matters, it must be asked for explicitly and reviewed separately.

### 3.4 What I would do differently

I would define the inter-component contracts (port numbers, table names, DTO field names, migration ordering) in a shared reference document at the start of the sprint and paste the relevant section into every AI prompt. This would have prevented the port-8001 mistake and the FK ordering failure with minimal extra effort. I would also write at least one "real shape" fixture test (using data copied from a live or seeded API response) before writing any AI-assisted component logic, so that DTO shape mismatches surface immediately rather than after several sessions of passing tests.
