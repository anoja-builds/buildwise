## 1. Overview

This log documents every AI-assisted session during the development of Component 4 of the BuildWise platform. The component covers the full quality assurance lifecycle: recording inspection outcomes against received deliveries, automatically raising Non-Conformance Reports (NCRs) for rejected material lines, and managing NCR resolution through a role-gated workflow. The most distinctive artefact is `quality_agent.py` — the largest Python microservice in the project at 7,286 bytes — which implements the `QualityRiskAnalysisAgent` and exposes two analytical endpoints on port 8004.

## 3. Reflection

### 3.1 What AI did well

AI tools accelerated the repetitive structural work that dominates a domain like quality management. Copilot was genuinely useful for generating the initial Pydantic model classes (`QualityRiskInput`, `QualityRiskOutput`, `NcrRecommendationOutput`) — the field names, types, and docstrings were syntactically correct and matched FastAPI's validation conventions without revision. It also produced a useful skeleton for the PowerShell verification script, getting the `Invoke-RestMethod` call structure, token acquisition function, and `Assert-True` helper right on the first attempt. Claude was helpful for drafting the NCR auto-raise logic inside the controller — the concept of reading `rejectedQuantity > 0` on each `InspectionItem` and creating a corresponding `NonConformance` was understood and implemented structurally correctly, even if the enum names were wrong. Gemini was useful as a sounding board when deciding to split the original combined `QualityPage` into two separate pages (`QualityInspectionsPage` and `NonConformancesPage`), articulating the separation-of-concerns argument clearly and suggesting the `qualityFormat.js` shared module to avoid duplication across both pages.

The `QualityLifecycleFlow.jsx` component (207 lines, 9 pipeline stages from Material Request through to Resolution) benefited from Copilot's ability to produce the repetitive `STAGES` array entries quickly. The overall architecture of the React risk panel — showing agent name, tool, execution source, risk level badge, and corrective action — was suggested by Copilot and was structurally sound, needing only style corrections.

### 3.2 Where AI failed or required correction

**Type and naming mismatches were the most consistent failure mode.** All three tools produced code that used string literals where enum values were required, or numeric types where string labels were expected. The `ncr_severity` field returning lowercase strings (`"high"`) instead of PascalCase enum-compatible values (`"High"`) is representative: the code appeared correct on a surface reading but produced silent data corruption when deserialised in C#. These bugs required careful cross-layer inspection — reading both the Python output and the C# consumer — to find.

**AI-generated tests regularly had missing or vacuous assertions.** The `test_high_rejections_high_risk` test body was left at `data = response.json()` with no assertion — a test that can never fail. This is a subtle and dangerous failure: the CI pipeline would have stayed green while the high-rejection path was completely untested. I now review every AI-generated test for the presence of at least one `assert` statement on the response data before accepting it.

**Prompt injection risk was introduced, not flagged.** Copilot's draft of `quality_agent.py` forwarded `item.rejection_reason` verbatim to the LLM prompt. In a quality management context, rejection reasons may contain supplier names, product codes, or adversarial text. Copilot did not warn about this; I identified the risk independently and resolved it by making the agent deterministic (no LLM call) rather than attempting to sanitise the input. This was the right architectural decision but required recognising the threat model, not just reviewing syntax.

**PowerShell-specific behaviour was not known to Copilot.** The `@()` coercion needed when a PowerShell object might return a scalar or an array is a subtle language quirk. Copilot's script omitted it, producing a verification check that appeared to pass (returning `$null.Count` is not an error in PowerShell, it just returns nothing) while actually not testing the assertion at all.

**The wrong module path in the Vitest mock** (`/quality` instead of `../services/qualityApi`) is a class of error Copilot makes frequently: it guesses plausible-looking import paths rather than reading the actual module structure of the project. Every generated test file must have its import paths verified against the actual file tree before trusting it.

### 3.3 Lessons learned

1. **Verify enum names across language boundaries immediately.** The C#-to-Python boundary is where type mismatches hide. After every session that touches both layers, I now run a quick integration check (or at minimum, compare enum values manually) before committing.
2. **Test test-code, not just production code.** AI-generated unit tests need to be tested: check that each test actually fails when the code is broken. Running `pytest` with the correct assertion deliberately negated is a 30-second check that would have caught the vacuous assertion problem on day one.
3. **Deterministic agents are safer than LLM-backed agents for compliance-critical domains.** For quality management — where NCR data may be used in legal or supplier-contract disputes — a deterministic rule-based agent is more defensible than an LLM one. The original design used an LLM; the final `quality_agent.py` uses no LLM at all, which also removed the prompt injection surface.
4. **Read every generated script in the target language's idiosyncrasies, not just for logical correctness.** PowerShell's scalar-vs-array coercion (`@()`) and JavaScript's `vi.mock` path resolution are language-specific pitfalls that general-purpose AI tools handle poorly because they generalise from the common case.

### 3.4 What I would do differently

In a future project I would establish a **cross-layer type contract file** (e.g., a shared JSON Schema or OpenAPI spec) before writing any agent code, so that enum value names are agreed between the C# models and the Python Pydantic schemas from the start rather than discovered through runtime failures. I would also require that any AI-generated test file be run with the production code intentionally broken (e.g., by changing a return value) before accepting it, to confirm that the tests actually exercise the logic. Finally, I would define the security threat model for each agent — particularly whether user-supplied text reaches the LLM — as a checklist item at the start of agent development, not as an afterthought discovered during code review.
